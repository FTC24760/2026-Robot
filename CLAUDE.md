# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

An FTC (FIRST Tech Challenge) robot for the 2026–2027 BIOBUZZ season. The code is an Android app built on FTC SDK 12.0. All team code lives in `TeamCode/`. `FtcRobotController/` is the stock SDK: don't edit it except to read its samples in `external/samples/`.

## Commands

Run these from the repo root (on Windows use `gradlew.bat` or `./gradlew` in Git Bash):

- Build: `./gradlew :TeamCode:assembleDebug`
- Install to a connected Control Hub: `./gradlew :TeamCode:installDebug` (Android Studio's Run button does the same thing)
- The Sloth plugin (`dev.frozenmilk.sinister.sloth.load`) is applied, so TeamCode can be hot-reloaded without reinstalling the app. Run its task from Android Studio's Gradle panel. The task name hasn't been checked here.
- The command line needs `JAVA_HOME` set (for example to Android Studio's bundled JBR). Without it, `gradlew` fails right away.

There are no unit tests. A change is only checked for real when it runs on the robot. "Tests" here means the hardware test OpModes in `opmodes/test/`. A clean `assembleDebug` is the most you can check from this machine.

## Architecture

Package root: `TeamCode/src/main/java/org/firstinspires/ftc/teamcode/`.

- **`Robot`** owns every subsystem plus `HubManager`, the Pedro `Follower`, `Controls`, `ShotSolver` and the Ivy commands. OpModes only forward lifecycle calls: `init → new Robot(this, alliance)`, `start → robot.start()`, `loop → robot.update()`, `stop → robot.stop()`. `Robot.update()` must call `hubManager.clearBulkCache()` first, because hubs use MANUAL bulk caching, so sensor reads are stale until the cache is cleared each loop. It then sets the loop timing (`robot.nowNs`, `robot.loopSeconds`) and the static `Robot.voltageScale`, which other classes read instead of timing things or reading the battery themselves. The loop order is listed in the `Robot` Javadoc.
- **Ivy (command-based)**: TeleOp runs on Ivy, Pedro Pathing's command library (`com.pedropathing.ivy:pedro`). The `Scheduler` is static: `Robot`'s constructor calls `Scheduler.reset()` and `Robot.update()` calls `Scheduler.execute()` once per loop. Commands live in `commands/` as static factories (`DriveCommands`, `ShotCommands`, `IntakeCommands`, `FlowerCommands`) and only set targets/flags on subsystems; `Robot.update()` writes the hardware after the Scheduler (`drivetrain.update()`, `shooter.update(nowNs)`, `intake.update()`, `flowerArm.refresh()`), so velocity loops and odometry run whatever is scheduled. Requirements are the subsystem objects; the intake is split into `intake.roller` and `intake.feeder` so intaking and shooting don't interrupt each other. `drive` uses `InterruptedBehavior.SUSPEND` so it resumes by itself after `tank` ends. Don't call `setEnd()` on a `sequential`/`parallel`/`race` group: it replaces the group's own end logic. Race it against `onInterrupt(...)` for cleanup instead (see `ShotCommands.shoot`). For autos, use `PedroCommands.follow(follower, path)` / `hold(follower)`.
- **`subsystems/`**: each mechanism implements `Subsystem` (`stop()`, `addTelemetry()`). A subsystem owns its hardware and never reads a gamepad. The usual pattern is: set public fields for what it should do (e.g. `intake.intakeOn`, `shooter.state`), then call its `update()` once per loop to write the hardware. `Robot` loops over the subsystem list for telemetry and stop, so a new subsystem must be added to that list.
- **Shooting**: `ShotCommands.autoAim` / `manualAim` (both require turret + shooter + hood, so one replaces the other) aim the turret and set the flywheel speed, and the hood follows `ShotSolver` in both; one of them always runs, starting on auto. `ShotCommands.shoot` is the shot sequence (wait for wheel at speed → open blocker → wait `BLOCKER_OPEN_TIME_MS` → feed) and runs while the shoot button is held; cancelling it closes the blocker and stops feeding. `utils/ShotSolver` supplies the auto-aim targets from the odometry pose and alliance: it aims at the nearer of our two CELLS (`AutoConstants.RIGHT_CELL_*`/`LEFT_CELL_*`, mirrored for blue by `utils/FieldPoses`), computes the turret bearing from the turret pivot, and gets RPM and hood from linear regressions fitted in Desmos (`ShooterConstants.RPM_SLOPE/RPM_INTERCEPT`, `HoodConstants.HOOD_INTERCEPT/HOOD_DISTANCE_COEF/HOOD_RPM_COEF`; distance in inches). The data comes from the `Test: Shot Tuning` OpMode, which runs the full robot with operator-set RPM/hood and saves (distance, RPM, hood) points.
- **Field pose**: odometry is in the field frame described in `AutoConstants` (inches, red/audience corner origin, heading 0 toward blue). `Robot` takes the alliance in its constructor, starts from `utils/PoseStorage.pose` (the auto leaves its final pose there) or the auto start pose, and operator X / B reset to `FieldConstants.RESET_POSE_1/2`. Field-centric drive is relative to our drivers via `Drivetrain.driverHeadingOffset`.
- **Units**: `Turret` works in radians to the left of robot forward; degree constants (servo range, deadbands) are converted inside the class. `TurretConstants.MANUAL_RATE` is rad/s.
- **Style**: plain public fields instead of getters/setters that only read or write a field. Keep a method only when it does more (clamping, writing hardware, derived values).
- **Butterfly / tank**: `DriveCommands.tank` runs while the driver's right stick Y is past `BUTTERFLY_THRESHOLD`: pods down, robot turns to face the left stick (stick up) or away from it (stick down) and drives with the stick projected on its forward axis (`Drivetrain.driveTank`). `Butterfly.update()`'s automatic mode is only used by `DriveTest`.
- **`controls/`**: one `Controls` class reads both gamepads (driver = gamepad 1, operator = gamepad 2) and turns them into intents; thresholds are in `ControlsConstants`. The button map is in its Javadoc. Ivy has no gamepad bindings, so `controls/Bindings` ties buttons to commands (`whileHeld`, `onPress`) and does the press/release detection; the bindings are registered in `Robot`'s constructor and `bindings.update()` runs each loop before `Scheduler.execute()`. Use `utils/EdgeDetector` for other press/toggle detection.
- **`constants/`**: all tunable numbers and hardware-config device names, as `public static` fields on `@Configurable` classes. These can be edited live from Panels (bylazar) on the robot, so don't hard-code tunables or device names in subsystems. Values marked `CALIBRATE` haven't been measured yet.
- **`opmodes/teleop/`**: `RobotTeleOp` (lifecycle base) → `MatchTeleOp` → `TeleOpRed` / `TeleOpBlue`. The alliance picks our HIVE, the start/reset poses and the field-centric direction.
- **`opmodes/test/`**: standalone single-mechanism OpModes (group `"Test"`) that build one subsystem directly instead of a full `Robot`. The exception is `ShotTuning` ("Test: Shot Tuning"), which runs the full `Robot` and sets `shotSolver.rpmOverride` / `hoodOverride` from the operator d-pad; A saves a point.
- **`pedro/`**: Pedro Pathing setup. `Constants.create(hardwareMap)` builds the `Follower` used by `Drivetrain` for field-centric drive and odometry. `Tuning` and `procedures/` are Pedro's tuner OpModes.
- **Vision**: a Limelight 3A (`subsystems/Vision`, `utils/HiveTracker`, `HiveCell`/`HiveSide`/`CellSide`) is only for detecting which CELL is up in auto; it is not built in TeleOp. TeleOp auto-aim comes from odometry (`ShotSolver`), with velocity lead and angular-velocity feedforward (`Turret.setFeedforward`).
- **Shooter logging**: `utils/AsyncRpmLogger` writes shooter RPM CSVs off the loop thread to `shooter_diagnostics/` on the robot. Pulled copies are kept in `shooter_logs/` at the repo root.

## Current state

The code is partway through a rewrite. TeleOp currently drives (mecanum, or field-oriented tank with the butterfly pods down while the driver holds right stick Y), intakes, aims the turret and hood (auto or manual), runs the shot sequence and toggles the flower arm, all as Ivy commands. Tank drive turns with Pedro's tuned heading controller (`ManualDrive.headingLock` with `pedro/Constants.foresightConfig`). Vision is deliberately not built in TeleOp: it is only for detecting which CELL is up in auto. The `opmodes/test/` OpModes don't use Ivy, except `ShotTuning` through `Robot`. Not wired up yet: the RPM/hood fit values (defaults hold `MANUAL_RPM` and the hood up until they're entered), `Shooter.isAtTargetRpm()` (a placeholder that always returns `true`), and the autonomous (which should set `PoseStorage.pose` when it ends). Update the comments when you change the behaviour they describe.
